# Web specification

Version: 1.0.0
Last updated: 2026-07-27

ID convention: `**WEB-n.**` leading tag at the start of each normative paragraph, sequential in document order, gaps allowed for later insertions. This matches `docs/DEPLOY_SPEC.md`'s placement convention rather than `docs/GRAPH_SPEC.md`'s trailing `{GRAPH-n}` tags, because this document is new and DEPLOY_SPEC is the more recent precedent in `docs/`.

This spec governs the React front end that replaces `web/conversation.html` and `web/clips.html`. Those two files are 146 KB of markup and JavaScript that already work and have been validated against the four worked examples in `tests/golden/`. They carry interaction behavior that took real debugging to get right and that no automated test covers, because it is a DOM-timing detail rather than a business rule. The purpose of this document is to make that behavior a checkable requirement of the rewrite instead of tribal knowledge that evaporates when the HTML is deleted.

The rules engine itself is out of scope here. This app is a thin client over `docs/BRIDGE_SPEC.md`'s `/evaluate`, `/polish`, `/transcribe`, `/criteria/{topic}` and `/health` endpoints. No hierarchy walk, threshold gate, scanner regex or justification template may exist in this codebase — see CLAUDE.md rule 1 and rule 5. Where this document and `docs/GRAPH_SPEC.md` or `docs/BRIDGE_SPEC.md` disagree about a data shape, those specs win.

## 1. Stack and structure

**WEB-1.** The app is Vite + React + TypeScript (`.tsx`), built as a static bundle and served from Firebase Hosting per `docs/DEPLOY_SPEC.md`. No server-side rendering — the bridge is the only server-side component, and it speaks JSON, not HTML.

**WEB-2.** Three routes: `/` (a two-card chooser, replacing the `web/index.html` that `docs/BRIDGE_SPEC.md` describes but that has never existed on disk), `/conversation`, and `/clips`. Route selection sets `context.mode` (`"conversation" | "clips"`, `STATE-3` in `docs/GRAPH_SPEC.md`) and nothing else — the mode is a single piece of state, not a build-time branch.

**WEB-3.** One component tree, driven by `context.mode`, not two parallel implementations. The original two HTML files already diverged in small, undocumented ways (see §10) precisely because they were maintained as separate files. A React rewrite that keeps them separate reintroduces the exact drift this repo exists to eliminate. Shared components (`SideNotesPanel`, `VerdictCard`, `JustificationBox`, `PicksGrid`, `IssuesList`) take `mode` as a prop or read it from context and render mode-appropriate fields per §7; only the handful of fields listed in §7 branch on it.

**WEB-4.** Local development runs the Vite dev server on its default port, `http://localhost:5173`, talking to the bridge at `http://127.0.0.1:8787` — genuinely cross-origin, unlike the retired HTML artifacts which were opened as local files or served same-origin from the bridge itself. A local production-build smoke test (`vite preview`) uses Vite's other default, `http://localhost:4173`, against the same bridge. Both origins are normative here because `docs/BRIDGE_SPEC.md`'s local-mode CORS allowlist must name the client's actual dev/preview origins rather than guess at them; if a contributor's environment needs a different port (a `--port` override, a container remap), the allowlist entry changes with it, not the other way around.

## 2. Auth gate

**WEB-5.** The app shows a sign-in screen before any form is reachable. Sign-in uses Firebase Auth's Google provider (`signInWithPopup` or `signInWithRedirect`; either is acceptable, redirect is more robust on mobile Safari). There is no anonymous or guest path — every route except the sign-in screen itself requires a signed-in user.

**WEB-6.** Once signed in, the client attaches the Firebase ID token as `Authorization: Bearer <token>` on every request to a `/api/**` path (which after the Hosting rewrite is same-origin — see `docs/DEPLOY_SPEC.md` for the rewrite). No request to the bridge is ever sent without this header; there is no unauthenticated code path left over from local `s2s serve` usage.

**WEB-7.** The client refreshes the token proactively rather than reactively: subscribe to `onIdTokenChanged` and keep the current token in memory, and call `getIdToken()` before a request if the cached token is within a short margin (for example 5 minutes) of Firebase's ~1 hour expiry. Do not wait for a `401`/`403` to trigger a refresh-and-retry loop as the primary mechanism — that pattern is a reasonable fallback for the rare race, not the main strategy, because it adds a full round trip of latency to a debounced live-update path that is supposed to feel instant.

**WEB-8.** A visible sign-out control calls Firebase Auth's `signOut()`, clears in-memory app state, and returns to the sign-in screen. Sign-out also clears any locally persisted draft per §11 — a shared or public machine must not retain a rater's notes after they explicitly sign out.

**WEB-9.** A signed-in user outside `@softical.tech` is a distinct case from not being signed in at all. Per `docs/DEPLOY_SPEC.md` (T1's 401-vs-403 clause), the bridge returns `401` when the `Authorization` header is missing or the token does not verify, and `403` when the token verifies but the account's email domain is not `softical.tech`. The client must branch on this distinction: a `401` sends the user back to the sign-in screen (their session is simply not established); a `403` keeps them on an explanatory screen stating that the signed-in Google account is not authorized for this tool because it is restricted to `@softical.tech`, with a control to sign out and try a different account. Never render a `403` as a generic "something went wrong" error — that erases the one piece of information the user actually needs.

**WEB-10.** The client may pass Google's `hd` (hosted domain) parameter to the sign-in call as a UX nicety — it pre-filters the Google account chooser toward `@softical.tech` accounts. This is a hint, not an enforcement mechanism: Google does not guarantee `hd` restricts which account a user can pick, and even if it did, a client-side parameter is trivially bypassed by an attacker who does not run the client's JS at all. The only authoritative check is the server-side domain check behind WEB-9. Do not let `hd` acquire any security meaning in this codebase, and do not remove the server-side check on the theory that `hd` already handles it.

## 3. Live update

**WEB-11.** The vanilla implementation calls its whole rules pipeline synchronously on every `input`/`change` event, because it was all local JavaScript. The React app has no local rules engine (that duplication is exactly what `docs/BRIDGE_SPEC.md`'s "Migration of the existing artifacts" section is deleting) so it must debounce: 250 ms after the last relevant field change, `POST /evaluate` with the current `EvaluationState` (`docs/GRAPH_SPEC.md` `STATE-17`), and render the response. Debounce restarts on every keystroke; it does not fire on a fixed interval.

**WEB-12.** While a request is in flight, the verdict/findings/justification panels keep showing their last-known-good content rather than blanking or spinning over it — replacing a readable draft with a spinner on every keystroke would be a visible regression from the original's zero-latency synchronous update. A small, unobtrusive indicator (for example a subtle pulse on the panel border, not a full-panel overlay) may show that a refresh is pending.

**WEB-13.** On a failed request (network error, 5xx, or a timeout the client enforces itself, suggested 10 s), the client keeps the last-known-good render, shows a small inline notice ("couldn't reach the server, retrying" or equivalent) near the verdict panel, and retries once automatically before falling back to a persistent-but-dismissible notice. It must never clear the form, never clear the draft, and never block further typing — the original artifacts had no network round trip and therefore no failure mode at all; the closest-fitting default is "degrade to stale-but-present," not "error page." A `401`/`403` on `/evaluate` is handled per WEB-9, not as a generic network failure.

**WEB-14.** The React app carries no client-side scanner. The vanilla `SIGNALS`/`TONE` regex tables and the `scanSignals()` matching logic are deleted, not ported — `docs/GRAPH_SPEC.md`'s `scan` node (`GRAPH-3`) runs server-side and its output arrives as the `suggestions` array in the `/evaluate` response (`docs/BRIDGE_SPEC.md`, one `Suggestion` per `STATE-15`: `side`, `target`, `kind`, `evidence`). The client's only job is to render each suggestion as a clickable chip and, on click, set the corresponding checkbox/field in local form state and let the next debounced `/evaluate` pick up the change — the same "accepting a suggestion is an explicit caller action" contract `docs/GRAPH_SPEC.md` `GRAPH-3` already states. Deleting the duplicated scanner is the point of this port; reimplementing even a subset of it in TypeScript defeats it.

## 4. The chip interaction invariant

This is the most important requirement in this document. Read it before touching the suggestion-chip component.

**WEB-15.** Invariant: a suggestion chip's DOM node must not be destroyed and recreated unless the underlying suggestion set has actually changed. This is stated as an invariant on outcome, not as a mandate to port the vanilla mechanism verbatim — see WEB-17.

**WEB-16.** Why this invariant exists. In the vanilla implementation, `recompute()` is bound to document-level `input` and `change` listeners and re-renders the suggestion chips from scratch (`host.innerHTML = ""` followed by rebuilding). Clicking a chip requires a `mousedown` and a `mouseup` on the same DOM node; a `click` never fires if the node is replaced in between. Clicking a chip also blurs the notes `<textarea>` the chip lives next to, which fires a `change` event, which re-enters `recompute()`, which rebuilds the chip list — destroying the very node the browser is mid-click on. Without a guard, a chip that is clearly visible and clearly clickable simply does nothing when clicked, with no error, no console warning, and no obvious reproduction path unless someone traces the event order by hand. The vanilla fix, `scanSignals()` in both original files, computes a signature `found.map(f => (f.box ? "1" : "0") + f.label).join("|")`, caches it in `host.dataset.sig`, and returns before touching `innerHTML` when the signature is unchanged from the last run. In the React app, the equivalent race is a debounced `/evaluate` response landing between a chip's `mousedown` and `mouseup` and causing a re-render of the suggestions list — the trigger moved from a synchronous DOM event to an async network response, but the failure mode is the same node-replacement-mid-click.

**WEB-17.** The idiomatic React solution is not a transliteration of the vanilla guard — do not port `dataset.sig` string-caching into a `useRef`. React already has the right primitives: give each rendered chip a stable `key` derived from content that does not change across a no-op suggestion refresh (for example `` `${side}:${kind}:${target}` ``, not an array index), and memoize the suggestions list (`useMemo` or `React.memo` on the chip-list component) against an equivalent signature of the incoming `suggestions` array so that an `/evaluate` response carrying the same suggestion set does not produce a new array reference that forces a re-render of already-mounted chips. Done correctly, React's reconciliation will not unmount and remount a chip whose key is unchanged, which satisfies WEB-15 without any manual DOM diffing. A future maintainer who "simplifies" this by removing the memoization, or by keying chips on array index, will reintroduce exactly the silent-dead-chip bug described in WEB-16 — this paragraph exists so that maintainer reads the reason before doing that.

## 5. Placeholder rendering

**WEB-18.** The placeholder token is the CJK lenticular bracket pair `【...】`, exact, per CLAUDE.md's guarded set. It is never rendered as an error, a warning icon, or a blocking state — a draft containing placeholders is correct, submittable-quality output per CLAUDE.md rule 4, because it correctly tells the rater what they still need to add in their own words.

**WEB-19.** Rendering order is normative: escape the draft text for HTML first, then match `/【([^】]*)】/g` against the escaped text, exactly as both vanilla files do (`esc(t).replace(/【([^】]*)】/g, ...)`). Matching before escaping would let rater-typed content that happens to contain `<`/`>`/`&` inside a placeholder's fill-in text corrupt the match or the resulting markup. The draft text itself comes from the server (`draft` or `polished` in the `/evaluate`/`/polish` response) and is never rater-authored HTML, but the escape-then-match order is still the contract to preserve, because a future change to what the server includes in a placeholder body (a rater's own quoted notes, for instance) must not silently reopen an injection path.

**WEB-20.** Prefer rendering the highlighted draft as React elements over `dangerouslySetInnerHTML`. Split the draft on the placeholder regex, map non-placeholder segments to plain text nodes and placeholder segments to a small `<Gap>` component (equivalent to the vanilla `.justbox em`, styled with `--warn`), and join into an array of children. This achieves the same visual result as the vanilla `hlGaps()` string-splice without constructing raw HTML from server text, which is the safer default in React and avoids re-deriving the escaping rule in two places (once server-side, once in a dangerouslySetInnerHTML string). If a future implementer chooses `dangerouslySetInnerHTML` instead for some reason, WEB-19's escape-before-match ordering still applies without exception.

**WEB-21.** The draft/polished text is never edited in place through this rendering step — clicking or interacting with a `<Gap>` does not delete or alter the placeholder. Filling in a placeholder is something the rater does by editing their own notes and letting the next `/evaluate`/`/polish` regenerate the draft, or by copying the draft out (§9) and editing it externally. There is no "click to fill" affordance in the originals and none should be invented here; that would be the UI silently doing the rater's job, which is exactly what CLAUDE.md rule 4 forbids the tool from doing.

## 6. Validation is advisory, never blocking

**WEB-22.** The findings returned by `/evaluate` (`docs/GRAPH_SPEC.md` `Finding`, `STATE-14`: `severity`, `code`, `label`, `message`) render as severity-colored cards (error/warning/info/ok, matching the vanilla `.issue.err/.warn/.info/.ok` styling) and nothing else. No button — Generate with AI assist, Rebuild from rules, Copy, Copy full task summary, Reset, or any future addition — is ever disabled, hidden, or gated based on finding severity, including `error`-severity findings. This is deliberate: the tool is a training surface where the rater makes their own call first and is shown where the rules disagree with them, per the project's north star in `criteria/project-criteria.md`. Making the tool refuse to let a rater proceed past a flagged contradiction would turn a coaching surface into a gatekeeper, which is a different product and one CLAUDE.md's design does not authorize. "Add proper validation" in the sense of disabling submission is exactly the improvement someone will make by habit, mistaking a training tool for a form-validation problem — this paragraph is the record that it was considered and rejected. Note that `/polish` itself does independently return `409` when blocking (`error`-severity) findings exist (`docs/BRIDGE_SPEC.md`), which governs whether the AI-assist request succeeds server-side; the client surfaces that `409`'s finding list inline rather than disabling the button pre-emptively, keeping the same "let the rater try, tell them why it didn't work" posture.

## 7. Mode deltas

**WEB-23.** Clips mode collects no Preflight block (`docs/GRAPH_SPEC.md` `STATE-10`, conversation-only), no per-side turn counts, no `task_success`, and no `prompts_used`. Its `TaskContext.prompt` and `TaskContext.ground_truth` fields are prominent (clips mode is a single shared prompt with an optional stated ground truth that drives premise findings), where conversation mode instead collects `TaskContext.scenario` and treats `ground_truth` as optional per `docs/GRAPH_SPEC.md` §5.

**WEB-24.** Conversation mode additionally has: the Preflight checklist (headphones, panning, scenario read, listened in isolation, equivalent prompts, stayed in character, interruption tested — `STATE-10`), per-side turn number inputs defaulting to 4 (§9), a `prompts_used` textarea (§10), per-side `task_success` (Pass/Partial/Fail), and a Knowledge Base tab (the vanilla `#viewKb` accordion content: north star, five-step workflow, hierarchy table, error-cluster list, common-mistakes list, "how to write a justification," the four worked examples, and the self-quiz). Clips mode has no equivalent second tab; its cheat-sheet content is a `<details>` panel alongside the form (vanilla `.acc` under "Criteria cheat sheet"), not a separate route or tab. Both the Knowledge Base tab and the cheat-sheet panel should be sourced from `GET /criteria/{topic}` (`docs/BRIDGE_SPEC.md`) rather than hardcoded JSX, so the two front ends and the CLI's equivalent help text cannot drift from `criteria/project-criteria.md` independently — this generalizes CLAUDE.md rule 5 (criteria live in `criteria/`, not in code) to the prose copy describing those criteria, not only the machine-checked thresholds.

**WEB-25.** Every field named in `docs/GRAPH_SPEC.md` `STATE-9` and `STATE-11` (`SideObservation`, `TaskContext`) that is not called out above as mode-specific is shared: raw notes, best/worst moment, error clusters, threshold checkboxes, background noise, premise handling, and the four picks (naturalness, utility, audio, overall). Error-cluster and threshold-checkbox label text differs slightly by mode in the vanilla files (compare conversation.html's "Interrupted me / talked over my turn" against clips.html's "an over-structured, assistant-style delivery" — the vanilla files use different catalog keys entirely for a few clusters, e.g. `robotic_intonation` and `over_structured` replace interruption-related clusters in clips mode, matching `docs/GRAPH_SPEC.md` §5's "Interruption-related clusters" row). The specific catalog and its keys are server-owned (`rules/catalog.py` and `criteria/`, per CLAUDE.md rule 5); the client renders whatever list the server returns for the active mode rather than hardcoding two label sets, so a criteria change never requires a client deploy.

## 8. Design tokens

**WEB-26.** Carry the existing CSS custom properties into a shared theme module (a single `:root` block or a TypeScript token object consumed by CSS-in-JS/CSS modules, either is acceptable): `--bg:#0e1014 --panel:#161a21 --panel2:#1c212a --line:#2a313d --txt:#e7ecf3 --dim:#9aa5b5 --acc:#6ea8fe --warn:#f5c451 --err:#f2777a --ok:#7dd3a0` plus per-side `--a:#7aa2f7` (Model A / Clip A) and `--b:#c98bdb` (Model B / Clip B). The vanilla files also define `--faint:#6b7686` and `--acc2:#8be9c0`; carry those forward too, they are used for secondary label text and Knowledge Base accents respectively.

**WEB-27.** The app is dark-theme only — there is no light-mode toggle in the originals and none is required here. Font stack is the system stack already in use (`-apple-system, BlinkMacSystemFont, "Segoe UI", Inter, Roboto, Helvetica, Arial, sans-serif`), with no external font loading (no Google Fonts `<link>`, no `@font-face` pointing at a CDN). This matters operationally, not just aesthetically: the deployed page should not issue requests to a third-party host on load, which keeps the page's network footprint limited to same-origin bridge calls after the Hosting rewrite (`docs/DEPLOY_SPEC.md`) and avoids a dependency on a CDN's uptime for a page rendering at all.

## 9. Smaller behaviors that are easy to lose in a rewrite

**WEB-28.** Reset restores per-side turn count inputs to `4`, not `0` and not empty — the vanilla `btnReset` handler explicitly sets `$("turnsA").value = 4; $("turnsB").value = 4` after clearing everything else, because 4 is the hard floor from `criteria/project-criteria.md`, not an empty/unset state. Losing this and defaulting to `0` or blank after a reset would silently reintroduce a below-minimum turn count that the validation would then have to re-flag on every fresh form. Reset in conversation mode is scoped to the form fields only (the vanilla `#viewForm` selector) and does not touch which tab (Rating Workspace vs Knowledge Base) is active.

**WEB-29.** Copy-to-clipboard (the draft, and in conversation mode the full task summary) uses the async Clipboard API (`navigator.clipboard.writeText`) when available, and falls back to a hidden, selected `<textarea>` plus `document.execCommand("copy")` when it is not — matching both vanilla files' `copy()`/`fallbackCopy()` pair. This fallback is not dead code to delete during the port: `execCommand("copy")` remains the only path in some embedded/webview contexts and older browser versions that lack `navigator.clipboard`, and a plain call to the async API in those contexts fails silently rather than throwing something obvious to catch in testing.

**WEB-30.** Conversation mode only: a "Copy full task summary" action (vanilla `btnSummary`, distinct from "Copy" which copies only the justification draft) that serializes scenario, scenario type, prompts used, both sides' full observation state, picks, the rules-engine outcome, and the current draft into one plain-text block for pasting into a ticket or a review thread. Clips mode has no equivalent button in the originals; do not add one as a "consistency" improvement without a product decision, since clips mode's state is smaller and the draft-only "Copy" already captures the substance of what a reviewer would need.

## 10. Pre-existing defects — recorded for a decision, not fixed here

These three defects exist in `web/conversation.html` and `web/clips.html` today. Porting either one silently (by copying the current behavior verbatim) or silently fixing it (by "correcting" it without a decision on record) both violate the point of this section, which is to make each one an explicit, visible choice for whoever implements the React app.

**WEB-31.** `creative` is missing from `web/conversation.html`'s `scenType` `<select>`. `docs/GRAPH_SPEC.md` `STATE-8` defines `ScenarioType` with eight values (`standard, redteam, premise, instruction, interrupt, emotional, roleplay, creative`); the conversation select offers only seven, omitting `creative`. `web/clips.html`'s `ptype` select offers a different six-value subset (`standard, premise, redteam, instruction, emotional, creative` — omitting `interrupt` and `roleplay`, which read as conversation-specific concepts). Recommendation: the React `<select>` for each mode should be generated from a single shared `ScenarioType` list filtered by an explicit per-mode allowlist defined once (not two independently hand-maintained option lists), and that allowlist should be a conscious decision about which scenario types make sense per mode rather than an accidental omission. Whether `creative` belongs in conversation mode, and whether `interrupt`/`roleplay` belong in clips mode, is a product decision this document does not make — flag it to `criteria-keeper` before implementation, since `ScenarioType`'s member set and its treatment are criteria-governed.

**WEB-32.** `frag()` — a helper that strips trailing `.`, `;`, `,` from a rater-typed field before splicing it into a sentence, so the generated justification does not read `"...its weak point was foo.."` or `"...foo.,"` — exists only in `web/clips.html` (`function frag(t){ return String(t||"").trim().replace(/[.;,]+$/,""); }`, used when splicing `best`/`worst` into `build()`). `web/conversation.html`'s `buildJustification()` splices `best`/`worst` into sentences raw, without this cleanup, so a rater who types "gave a concrete tip." into the "strongest moment" field gets visibly doubled punctuation in the draft. This asymmetry has no criteria basis — it looks like an omission in conversation.html rather than an intentional difference. Since this string-splicing now happens server-side in the `draft` node (`docs/GRAPH_SPEC.md` `GRAPH-7`), the fix, if made, belongs in `rules/draft.py` for both modes uniformly, not in this client. Recorded here so the drafting spec/implementation owner (`rules-engine-dev`) picks it up rather than it silently persisting as a conversation-mode-only rough edge in the rewrite.

**WEB-33.** `prompts_used` is typed `list[str]` in `docs/GRAPH_SPEC.md` (`STATE-11`), but `web/conversation.html` collects it as a single newline-delimited `<textarea>` (`id="prompts"`) and never splits it — the raw multi-line string is passed straight through to `buildAIPrompt()`'s "Prompts used: ..." block and to `fullSummary()`. No client-side `.split("\n")` exists anywhere in the current code. Decision needed and recorded here: either (a) the client keeps the newline-delimited textarea as the input affordance but splits on `\n`, trims, and drops empty lines before sending `prompts_used` as a proper `list[str]` in the `/evaluate` body, or (b) the client sends the raw string in a distinct field and the server does the splitting during `ingest` (`docs/GRAPH_SPEC.md` `GRAPH-1`, which already normalizes three different payload shapes into `EvaluationState`). Recommendation: (a), client-side split at the form boundary — `ingest`'s job is reconciling three payload *shapes* (CLI answers, bridge JSON, replayed run file), not parsing free text within a field, and a bridge JSON payload should already conform to the typed schema it claims to satisfy. Whichever option is chosen, `docs/GRAPH_SPEC.md` does not need to change; only the client's serialization step does.

## 11. Local draft persistence

**WEB-34.** Decision: the React app persists the in-progress form as JSON to `sessionStorage`, keyed by mode (`s2s-draft-conversation` / `s2s-draft-clips`), on every successful state update (debounced with the same cadence as §3, not on every keystroke separately). Neither vanilla artifact has any `localStorage`/`sessionStorage` use today — a page refresh currently loses a part-written evaluation entirely, with no undo.

**WEB-35.** Reasoning: rater notes describe a voice model's behavior during a scripted evaluation task, not the rater's own personal information, and the app already sits behind the Firebase Auth gate in §2 restricted to `@softical.tech` — so the marginal exposure from a local persistence layer is small and is bounded by who already has access to the signed-in browser session, not by who can reach the deployed URL. Against that small risk sits a concrete, likely cost: the form has upward of twenty free-text and structured fields per side, filling it out takes real time, and an accidental refresh, a browser crash, or a laptop sleep/wake glitch destroying twenty minutes of typed observations with no warning and no recovery path is the kind of failure that erodes trust in the tool itself, independent of whether the rules engine is correct.

**WEB-36.** `sessionStorage` is chosen over `localStorage` specifically: it satisfies the actual failure mode this decision is about (an accidental refresh or navigation within the same tab) while auto-clearing when the tab or browser closes, rather than leaving rater notes resident on disk indefinitely. This trades away recovery from "closed the tab on purpose, meant to come back tomorrow" — accepted, because that case is a deliberate action with an obvious mitigation (do not close the tab, or accept that the draft is gone), whereas a mid-task refresh is an accident. The persisted draft is cleared explicitly on: the Reset button (§9), a successful sign-out (WEB-8), and should be considered for clearing after a task summary copy or explicit "start new task" action if one is added — but is deliberately not auto-cleared on every `/evaluate` success, since the draft is still "in progress" for as long as the rater is looking at it. No token, credential, or auth state is ever written to `sessionStorage` under this decision — that remains the Firebase SDK's own persistence mechanism, untouched by this clause.

## Traceability

This spec is new; it supersedes no existing clause. It should be read alongside `docs/BRIDGE_SPEC.md` (endpoint shapes, migration-of-artifacts section) and `docs/GRAPH_SPEC.md` §1 and §5 (state schema and mode differences), both of which this document defers to on data shape. `docs/DEPLOY_SPEC.md` governs the Hosting rewrite, the same-origin consequence referenced in WEB-6, and the 401-vs-403 semantics referenced in WEB-9.
