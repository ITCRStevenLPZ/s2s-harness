# Deployment specification

Version: 2.0.0
Last updated: 2026-07-27

Change note (2.0.0): This is a breaking change to the auth and network model, not an addition, so the version bumps a major, not a minor. It replaces the Wave 1 app-level API key (`X-S2S-Key`, shared secret, `hmac.compare_digest`) with Firebase ID-token verification, and replaces the Wave 1 external HTTPS load balancer plus Cloud Armor with a Firebase Hosting rewrite as the front door. Superseded clauses are marked deprecated in place per the CLAUDE.md deprecation rule; none are deleted. The replacement mechanism is DEPLOY-27 through DEPLOY-33 in the new section 3a.

ID convention: `**DEPLOY-n.**` leading tag at the start of each normative paragraph, sequential in document order, gaps allowed for later insertions. This differs in placement from T1's trailing `{RULE-n}`-style tags used in the engine-facing specs; confirmed with T1 via the durable record (`team_findings.md`, "[T1 -> T5-gcp-deploy] ID convention reply") that this is fine as-is: `DEPLOY-n` and T1's six prefixes are disjoint namespaces in disjoint files, so visual placement does not need to match across the two halves of `docs/`. What matters and does match: the `Version` / `Last updated` header block directly under the H1.

This spec governs the hosted deployment of the bridge (`docs/BRIDGE_SPEC.md`) on GCP Cloud Run. It exists because the user has decided to host the harness remotely, which directly contradicts the loopback-only, no-auth posture that `BRIDGE_SPEC.md` and `ARCHITECTURE.md` originally specified for a single rater on a local machine. Those clauses are not deleted, they are marked deprecated in place in their home documents, pointing here. Loopback-only remains correct and binding for `s2s serve` run locally; nothing in this document changes that path. Everything in this document applies only when the bridge runs as a Cloud Run service.

No infrastructure described here has been applied. This is the design; `deploy/terraform/` is the implementation, validated but never `apply`d by this wave.

## 1. Deployment target

**DEPLOY-1.** The bridge deploys as a single stateless container to Cloud Run.

The bridge (`docs/BRIDGE_SPEC.md`) is a single-process FastAPI app with no persistent state of its own, `EvaluationState` lives in the request/response cycle, and the only durable artifact is the content-addressed polish cache under `.s2s-cache/`, which is a local performance optimization, not a correctness dependency (`docs/ARCHITECTURE.md`, Draft-hash caching). Each `/evaluate` call is a complete run: nothing needs to survive past the response. That makes Cloud Run's request-scoped, horizontally-scaled model a fit without any redesign of the engine.

**DEPLOY-2.** `min-instances = 0` (scale to zero). There is exactly one rater. Paying to keep a container warm for a service with no continuous traffic is waste, and scale-to-zero has no correctness cost here because the app holds no in-memory state across requests that matters once a run completes.

**DEPLOY-3.** *(Amended in 2.0.0.)* `max-instances` is capped (default 2, a Terraform variable) to bound both cost and the blast radius of any abuse that gets past the Firebase Hosting front door and the Firebase ID-token check (DEPLOY-27, DEPLOY-31). This is not a capacity plan, a single rater does not need concurrency, it is a ceiling. Original 1.0.0 text, retained for the record: "to bound both cost and the blast radius of any abuse that gets past Cloud Armor and the API key check." Cloud Armor is retired (DEPLOY-7, deprecated) and the API key is retired (DEPLOY-9 through DEPLOY-12 and DEPLOY-14, deprecated); `max-instances` now sits behind fewer other layers than it did in 1.0.0, not the same number with different names. See DEPLOY-8's amended defense-in-depth discussion and the security-tradeoff note that follows it.

**DEPLOY-4.** No database, no attached persistent volume, no session store. See §8.

## 2. Network posture

*(2.0.0: the load balancer and Cloud Armor model described in DEPLOY-5 through DEPLOY-7 below is retired. The current front door and ingress model is DEPLOY-31 and DEPLOY-32 in section 3a. DEPLOY-5 through DEPLOY-7 are kept below, marked deprecated in place, for the historical record and so nothing referencing them by id goes dead.)*

**DEPLOY-5.** **Deprecated, superseded by DEPLOY-31 (Firebase Hosting rewrite as front door).** Originally: "Public entry is an external HTTPS Application Load Balancer with a Google-managed TLS certificate, fronting a serverless NEG that targets the Cloud Run service." The load balancer stack in `deploy/terraform/network.tf` (regional NEG, backend service, url map, managed SSL certificate, target HTTPS proxy, global address, global forwarding rule, plus the Cloud Armor policy of DEPLOY-7, eight `google_compute_*` resources in total) is retired. Firebase Hosting's own edge and the `/api/**` rewrite (DEPLOY-31) are the public entry now.

**DEPLOY-6.** **Deprecated, superseded by DEPLOY-32 (required Cloud Run ingress under the Hosting-rewrite arrangement).** Originally: "The Cloud Run service's ingress setting is `internal-and-cloud-load-balancing` (the `gcloud`/API surface name; the Terraform/REST enum for the same setting is `INGRESS_TRAFFIC_INTERNAL_LOAD_BALANCER`, used in `deploy/terraform/cloud_run.tf`). The service is never directly reachable at its default `*.run.app` URL; every request must traverse the load balancer." This is no longer achievable once the load balancer of DEPLOY-5 is retired: a Firebase Hosting rewrite invokes the Cloud Run service at its default `run.app` URL directly, not through Google Cloud Load Balancing infrastructure, and `internal-and-cloud-load-balancing` ingress would block that invocation path along with everything else it blocks. Ingress becomes `all` under the new arrangement; DEPLOY-32 cites the verification for this.

**DEPLOY-7.** **Deprecated, retired with no replacement.** Originally: "A Cloud Armor security policy is attached to the load balancer's backend service, providing rate limiting (per-IP request throttling) and an optional IP allowlist, defaulted off but wired so the operator can turn it on without a redeploy." Cloud Armor attaches to a load balancer backend service; there is no load balancer to attach it to once DEPLOY-5 is retired. This is a genuine reduction in volumetric defence, not a like-for-like swap for something else. See the security-tradeoff note after DEPLOY-8 for what this means operationally and what to do about it if the deployment's scope ever widens.

**DEPLOY-8.** *(Amended in 2.0.0.)* Defense in depth is thinner now than it was in 1.0.0, and this clause says so plainly rather than restating the old argument with new nouns substituted in. The Firebase ID-token check (DEPLOY-27 through DEPLOY-30) is the identity control: it answers "is this caller authorized." There is no volumetric or origin control layered on top of it anymore. Cloud Armor is retired (DEPLOY-7) with no replacement, and Firebase Hosting's edge network provides DDoS-scale absorption and static-asset caching but not per-IP rate limiting or an IP allowlist. What remains between a plausible-looking request and the application is: `max-instances = 2` (DEPLOY-3), which is a cost and blast-radius ceiling, not a rate limiter; the ID-token check itself, which rejects unauthenticated or wrong-domain traffic but does not throttle a high volume of correctly-authenticated requests from a compromised or phished `@softical.tech` account; and Firebase Hosting's edge, which is a CDN and TLS terminator, not a WAF. Original 1.0.0 text, retained for the record: "This is deliberate defense in depth, not redundancy. The app-level API key (§3) is the identity check, it answers "is this caller authorized." Cloud Armor is the volumetric and origin control, it answers "is this traffic pattern abusive, regardless of whether the key is valid." A leaked key without Cloud Armor still lets an attacker hammer the service; Cloud Armor without a key lets anyone who reaches the LB in. Neither substitutes for the other."

**Security tradeoff, stated plainly, not a footnote:** retiring Cloud Armor removes per-IP rate limiting and the IP allowlist from this deployment's defenses. For a single authenticated rater on an allowlisted domain, this is an acceptable and deliberate simplification: it trades away a control this project was not actively using (Cloud Armor's IP allowlist defaulted off in 1.0.0 per the original DEPLOY-7, and its rate limiter carried no operator-configured threshold) for one fewer piece of infrastructure to run, pay for, and keep correctly configured. It stops being acceptable the moment this service becomes multi-rater or public-facing. If that happens, the operator must reinstate a volumetric control before widening access: either restore the DEPLOY-5 through DEPLOY-7 load balancer and Cloud Armor stack (the Terraform for it still exists, it is simply unwired from the Hosting rewrite, and DEPLOY-32's ingress setting would need to revert alongside it), or adopt whichever current GCP-recommended integration exists at that time for attaching volumetric protection in front of a Firebase Hosting site. Do not scale `@softical.tech` access to a wider audience on the strength of the auth check alone; the auth check answers who, not how much or how fast.

## 3. Authentication

*(Rewritten in 2.0.0.)* The deployed bridge required an app-level API key in 1.0.0. DEPLOY-9, DEPLOY-10, DEPLOY-11, DEPLOY-12, and DEPLOY-14 describe that shared-secret mechanism and are marked deprecated in place below; DEPLOY-13 and DEPLOY-15 are unchanged in substance and kept. The shared-secret mechanism is superseded by Firebase ID-token verification, DEPLOY-27 through DEPLOY-30 in section 3a. `docs/BRIDGE_SPEC.md`'s original "no auth, loopback-only" posture remains superseded for this deployment mode only, per the deprecated markers in that file; this section (together with 3a) is still the normative source for hosted-mode auth behavior, implemented at `BUILD_PLAN.md` Phase 7.

**DEPLOY-9.** **Deprecated, superseded by DEPLOY-27.** Originally: "Location: `src/s2s_harness/bridge/auth.py`. Implemented as a FastAPI dependency (or `Depends`-injected middleware) applied to every route except the one exempted in DEPLOY-13." The module location and the dependency-injection pattern are unchanged and continue to apply to the Firebase verification module of DEPLOY-27; only the verification logic inside the module changes, from shared-secret comparison to public-key signature verification of a bearer token.

**DEPLOY-10.** **Deprecated, superseded by DEPLOY-27.** Originally: "Header: `X-S2S-Key`. The client sends the shared secret in this header on every request." Replaced by `Authorization: Bearer <idToken>`, a standard bearer-token header carrying a Firebase Auth ID token rather than a static shared secret.

**DEPLOY-11.** **Deprecated, superseded by DEPLOY-27.** Originally: "Comparison: `hmac.compare_digest(provided, expected)`. Never `==` and never a `startswith`/substring check. A naive equality comparison on a secret short-circuits on the first mismatched byte, which leaks timing information proportional to how many leading bytes are correct, a real, exploitable side channel against a shared secret, not a theoretical one. `hmac.compare_digest` runs in constant time regardless of where the mismatch occurs." Firebase ID-token verification is not a secret-comparison problem: there is no stored secret value on the server to compare a client-supplied value against. The token is verified by checking a cryptographic signature against Google's rotating public keys, an asymmetric-key operation, not a constant-time equality check. `hmac.compare_digest` has nothing to guard once there is no shared secret to guard.

**DEPLOY-12.** **Deprecated, superseded by DEPLOY-16 (edited) and DEPLOY-33.** Originally: "The key itself is never hardcoded, never checked into `deploy/`, and is read from the environment at startup (populated from Secret Manager per §4). Missing key at startup is a hard failure, see DEPLOY-14." There is no key to store, so DEPLOY-16's secret list drops `s2s-app-api-key` entirely rather than replacing it with a new secret. What still needs a hard startup check is the Firebase project configuration the verification library needs, per DEPLOY-33, which inherits this clause's "fail loud at boot" discipline for the new mechanism.

**DEPLOY-13.** `GET /health` is exempt from the auth check, whichever mechanism is current (the Firebase ID-token check of DEPLOY-27 today; the retired key check of DEPLOY-9, deprecated, in 1.0.0). This clause's reasoning is auth-mechanism agnostic and unchanged by the 2.0.0 switch: the front door's own health probe and the front end's availability badge (`docs/BRIDGE_SPEC.md` `GET /health`) both need to reach it unauthenticated, and a health check cannot be taught to carry a bearer token without becoming another credential to manage. Its response body, `{"ok": true, "stt": "gemini", "llm": true, "version": "<semver>"}` (`version` read via `importlib.metadata.version("s2s-harness")` per `VERSIONING.md`, confirmed with `ci-dev`), was reviewed in 1.0.0 and remains judged safe to expose without auth: it names which STT provider class is configured (not credentials), whether the polish path is enabled (a boolean, not a key), and the running semver. None of that is a secret, a capability grant, or information that materially assists an attacker beyond what "this is an S2S harness bridge" already reveals from the response shape itself. Nothing about this clause changes with the auth mechanism swap; only the name of the thing it is exempt from changes.

**DEPLOY-14.** **Deprecated, superseded by DEPLOY-29 (401 vs 403) and DEPLOY-33 (startup discipline).** Originally: "Every other endpoint returns `401` when the header is absent or the key does not match. There is no "allow if unset" fallback. A missing `S2S_APP_API_KEY` (or equivalent) in the environment is a startup error, not a silent open door, this mirrors `docs/STT_SPEC.md` §8's rule for a missing STT credential ("Never silently degrade"). The same discipline applies to the auth boundary: an unconfigured key must fail loud at boot, not fail open at request time." The binary "match or 401" model does not carry over cleanly: the new mechanism has two distinct failure shapes (unauthenticated versus wrongly-authenticated), so DEPLOY-29 replaces the response-code half of this clause and DEPLOY-33 replaces the startup-discipline half. Neither half is weakened, both are more precisely specified than before.

**DEPLOY-15.** `src/s2s_harness/bridge/auth.py` must not import from `src/s2s_harness/rules/`. Authentication is a transport concern; the rules layer stays pure per `docs/ARCHITECTURE.md`'s layer-boundary table (`rules/` may not be imported by `cli/`, `bridge/` directly, go through the graph). This keeps the token-boundary AST test (`tests/test_layering.py`) passing without a carve-out. This constraint is unchanged by the 2.0.0 mechanism swap and applies identically to the Firebase verification code introduced by DEPLOY-27: same file, same boundary, only the internals of what the module does changed.

## 3a. Firebase authentication and front door

*(New in 2.0.0.)* Replaces DEPLOY-9 through DEPLOY-12 and DEPLOY-14 (shared-secret auth) and DEPLOY-5 through DEPLOY-7 (load balancer and Cloud Armor). New clause ids continue from DEPLOY-26; nothing above is renumbered.

**DEPLOY-27.** Every request to a non-exempt route (the exemption is DEPLOY-13) must carry `Authorization: Bearer <idToken>`, where `<idToken>` is a Firebase Auth ID token minted client-side by the Firebase JS SDK after sign-in. The bridge verifies it server-side before the request reaches any route handler: signature against Google's current public keys (rotated automatically; the verifying library fetches and caches them, there is no key material the bridge itself manages or stores), audience equal to the Firebase project id, issuer equal to `https://securetoken.google.com/<project-id>`, and expiry (`exp`/`iat`) not passed. Library: `google-auth`'s `google.oauth2.id_token.verify_firebase_token()`, from the `google-auth[requests]` optional dependency (the `[requests]` extra supplies the `google.auth.transport.requests.Request` transport the verifier needs; plain `google-auth` has no bundled HTTP transport). This choice was made and already implemented by T4 (`pyproject.toml`, a new `bridge-auth` optional-dependency group, SHA `8e7e021`), not `firebase-admin`: `verify_firebase_token` verifies audience, issuer, and `iat`/`exp` against Firebase's public certificates and is sufficient because the bridge only ever verifies ID tokens, it never mints custom tokens, manages users, or reads Firebase user records, so the full Admin SDK's extra surface (user management, custom claims, Firestore/RTDB integration) would be pure overhead for a single-purpose verification dependency. This spec records that decision rather than the `firebase-admin` alternative first considered; the dependency itself is T4's to add and already added.

**DEPLOY-28.** The `@softical.tech` domain constraint is enforced server-side, on the `email` claim of the verified token (after DEPLOY-27's verification and DEPLOY-30's `email_verified` check), never on a client-supplied value. Firebase Auth's `hd` (hosted domain) hint, settable on the client-side Google sign-in provider, restricts which accounts the hosted sign-in picker offers to choose from. That is a UX affordance that makes the intended path easy to reach, and nothing more. A request carrying a valid ID token for a real, non-`@softical.tech` Google account, sent directly to the API rather than through the hosted sign-in picker, bypasses any client-side `hd` restriction trivially: the hint is not part of the token's verified claims and the bridge has no way to check it even if it wanted to. The domain check belongs entirely to the server, applied to the verified claim, every time.

**DEPLOY-29.** The bridge distinguishes two failure shapes on the auth path, and the frontend renders them differently:

- `401 Unauthorized`: the request has no `Authorization` header, the header is malformed, the token fails signature, issuer, or audience verification, or the token is expired. This is "we do not know who you are"; the frontend's response is to send the rater back through sign-in.
- `403 Forbidden`: the token verifies and identifies a real, currently-authenticated Google account, but that account's email is outside `@softical.tech` (or its `email_verified` claim is false, DEPLOY-30). This is "we know who you are and you are not allowed"; the frontend's response is a distinct message naming the domain restriction, not a generic "please sign in again," because routing an already-authenticated-but-wrong-account rater back through the same sign-in flow without explanation just reproduces the same 403 a second time.

**DEPLOY-30.** The `email_verified` claim on the verified token must be checked true before the `@softical.tech` suffix match runs, not after, and not skipped. Firebase Auth issues tokens for accounts with unverified emails (for example, a federated identity provider that does not itself guarantee verification, or an email/password account before the rater clicks the verification link). A suffix match against an unverified `email` claim is checking a value the identity provider has not attested to, which is not the same thing as checking that the authenticated account is actually `@softical.tech`. An attacker-influenced or provider-default email that happens to match the suffix on an unverified account must not be allowed to pass the domain check.

**DEPLOY-31.** Firebase Hosting is the public front door. Its rewrite configuration (`firebase.json`, deploy configuration rather than application code, not owned by this file) sends `/api/**` to the Cloud Run service; every other path is served from Hosting's static bucket (the React build described in `docs/WEB_SPEC.md`). Because both the static frontend and the API are served from the same Hosting origin, this is same-origin end to end: there is no cross-origin request from the browser to the bridge, and no CORS allowlist to maintain for the hosted deployment. `docs/BRIDGE_SPEC.md`'s CORS-to-DEPLOY_SPEC cross-reference has been dangling since Wave 1 (DEPLOY_SPEC has never had a CORS clause); this arrangement makes that reference moot rather than fixing it, and says so explicitly here so the dangling reference is not mistaken for something this 2.0.0 change resolved. T2 owns closing that reference out in `BRIDGE_SPEC.md`.

**DEPLOY-32.** Cloud Run ingress is `all`, not `internal-and-cloud-load-balancing`.

Verified against current GCP documentation, not assumed: Google's Cloud Run ingress-settings page (`docs.cloud.google.com/run/docs/securing/ingress`, fetched 2026-07-27) lists Firebase Hosting among the services that invoke Cloud Run via the service's default `run.app` URL, and states that disabling that default URL "prevents [Firebase Hosting] from working as expected." The same page defines `internal-and-cloud-load-balancing` as blocking direct `run.app` URL access from the internet and admitting traffic only from Google Cloud Load Balancing infrastructure (an External Application Load Balancer) or internal VPC sources. Firebase Hosting's rewrite proxy is not that load-balancing infrastructure; it invokes the public `run.app` URL directly. So `internal-and-cloud-load-balancing` would block the Hosting rewrite's own requests to the backend, not just unwanted direct traffic. `all` is required for the rewrite path to reach the service at all. Independently corroborated by community deployment guides describing the same requirement in practice (for example, "How to Use Firebase Hosting Rewrites to Route Traffic to Cloud Run Services," oneuptime.com, 2026), though the GCP ingress-settings page is the primary source cited here.

This is the ingress half of the security tradeoff recorded after DEPLOY-8. Setting ingress to `all` means the service is reachable at its `run.app` URL directly, bypassing Firebase Hosting, not bypassing the auth check: DEPLOY-27's verification runs in application code as a FastAPI dependency, not at the network layer, so a direct `run.app` request still hits the same dependency and is still rejected without a valid `@softical.tech` bearer token. What ingress `all` gives up is DEPLOY-6's retired network-layer guarantee that every request had already traversed a controlled front door before reaching application code; what stays true regardless of which path a request took is that it still needs a valid token to get past the first line of code that runs.

On header preservation: the design in DEPLOY-27 depends on the `Authorization` header surviving the Firebase Hosting rewrite unmodified on its way to Cloud Run. Current documentation does not state this as a single explicit guarantee for the `Authorization` header by name. What is documented: Firebase Hosting strips `Cookie` headers except for `__session` on rewritten requests, and Google's edge removes a short, named list of hop-by-hop headers on requests to Cloud Functions (`Connection`, `Keep-Alive`, `Proxy-Authorization`, `TE`, `Trailer`, `Transfer-Encoding`, and headers matching `X-Google-*`); `Authorization` is not on that list. Separately, sending `Authorization: Bearer <idToken>` through a Firebase Hosting rewrite to a Cloud Run or Cloud Functions backend and verifying it server-side is a pattern Google itself documents and that appears repeatedly across Firebase and Cloud Run integration guides as the standard way to protect a rewritten API route. This is corroborating evidence from multiple consistent sources, not one canonical sentence naming `Authorization` specifically as preserved. Admitted gap: this should be confirmed with a live smoke test against the actual `firebase.json` rewrite configuration during implementation (Wave 3b or 3c), before the design is relied on in production. If the header is ever found to be altered or dropped in practice, Cloud Run's own IAM-based auth layer documents `X-Serverless-Authorization: Bearer <idToken>` as an alternate header intended for exactly this kind of intermediary rewriting, and that would be the fallback transport, not a redesign of DEPLOY-27's verification logic.

**DEPLOY-33.** Startup failure discipline, inheriting DEPLOY-14's principle even though DEPLOY-14 itself is deprecated: a missing or unparseable Firebase project configuration (the Firebase project id that DEPLOY-27's `verify_firebase_token()` call passes as `audience` and checks each token's `aud` claim against) is a hard startup error. The bridge must refuse to start rather than start in a mode where token verification silently no-ops or falls back to accepting any bearer value. This mirrors `docs/STT_SPEC.md` §8's "Never silently degrade" rule, the same rule DEPLOY-14 cited for the retired key mechanism: an unconfigured auth boundary fails loud at boot on this mechanism exactly as it did on the old one. Nothing about switching mechanisms is a license to relax this.

## 4. Secrets

**DEPLOY-16.** *(Edited in 2.0.0.)* Secret Manager holds two secrets: `anthropic-api-key`, `gemini-api-key`. Each is injected into the Cloud Run service as a secret environment variable reference (`--set-secrets` / the Terraform `google_cloud_run_v2_service` `env` block with `value_source.secret_key_ref`), never baked into the container image and never passed as a plain Terraform `env` string. Originally this list also held `s2s-app-api-key`; it is removed, not replaced, because the shared secret it held no longer exists under Firebase ID-token verification (DEPLOY-27), there is nothing left to compare a header value against, so there is nothing left to store. The Firebase project id used for token verification (DEPLOY-27's `aud` check) is not a secret: it is public by design, already embedded in the client-side Firebase web configuration shipped in the React build (`docs/WEB_SPEC.md`), and needs no Secret Manager entry. See DEPLOY-33 for how the bridge obtains and validates that configuration at startup.

**DEPLOY-17.** `GOOGLE_APPLICATION_CREDENTIALS` (the service-account JSON file path documented in `.env.example` for local use) is dropped entirely in the deployed configuration. The Cloud Run runtime service account (§5) supplies Application Default Credentials automatically via the attached identity; there is no JSON key file to mount, rotate, or leak. This removes an entire secret and an entire file-mount from the threat model compared to the local-dev path, it is a strict improvement, not a parity gap. `.env.example` continues to document `GOOGLE_APPLICATION_CREDENTIALS` for local use only; that file is T4-owned and any deployment note there is theirs to add.

**DEPLOY-18.** `S2S_STT_PROVIDER=gcp` deployments therefore authenticate purely via the runtime SA's ADC. `S2S_STT_PROVIDER=gemini` deployments still need `gemini-api-key` from Secret Manager, since Gemini API access is a bearer key, not an IAM-federated identity.

## 5. IAM

**DEPLOY-19.** A dedicated Cloud Run runtime service account (`s2s-runtime@<project>.iam.gserviceaccount.com`) is created and attached to the service. The default compute service account is never used, and no role is granted at the project-Owner/Editor level.

**DEPLOY-20.** Grants, least privilege:

| Role | Scope | Condition |
|---|---|---|
| `roles/secretmanager.secretAccessor` | Per-secret, on each of the two individual secret resources | Always |
| `roles/speech.client` | Project | Only if `S2S_STT_PROVIDER=gcp` is enabled for the deployment |

No `roles/editor`, no `roles/owner`, no broad `roles/secretmanager.admin`. Secret access is bound to the specific secret resource, not granted project-wide, so compromising the runtime SA does not expose secrets this deployment does not use. *(2.0.0: this table held a per-secret grant across three secret resources in 1.0.0; it is two now, following DEPLOY-16's removal of `s2s-app-api-key`. There is no accessor grant to remove separately, since a grant on a secret that no longer exists is simply not created.)*

## 6. Supply chain

**DEPLOY-21.** Container images are stored in Artifact Registry with vulnerability scanning enabled on the repository.

**DEPLOY-22.** Deploys reference the image by immutable digest (`@sha256:...`), never by a mutable tag such as `:latest` or `:main`. A tag can be repointed after the fact; a digest cannot. This is what makes "what is actually running" a verifiable question instead of a trust claim. `release.yml` pushes two tags on every release, `<registry-path>:X.Y.Z` and `<registry-path>:<full-commit-sha>`, both pointing at the same digest, tag format itself is fixed in `VERSIONING.md` (owned by `ci-dev`), not duplicated here; this clause is about what Cloud Run deploys from, which is the digest, never either tag.

**DEPLOY-23.** CI authenticates to GCP via Workload Identity Federation for GitHub Actions OIDC. No long-lived service-account JSON key exists anywhere, not in GitHub Actions secrets, not on disk, not in this repo. Confirmed in writing with `ci-dev` (`team_findings.md`, "[T5 <-> T4-ci-dev] WIF and registry naming confirmed"):

- WIF pool: `github-pool`. Provider: `github-provider`. Full provider resource name for the `google-github-actions/auth` action's `workload_identity_provider` input: `projects/<PROJECT_NUMBER>/locations/global/workloadIdentityPools/github-pool/providers/github-provider` (project *number*, not project ID; read from `terraform output workload_identity_provider` after apply).
- Deploy service account release.yml assumes: `s2s-deployer@<project-id>.iam.gserviceaccount.com`.
- Registry path: `<region>-docker.pkg.dev/<project-id>/s2s-harness/bridge` (region defaults to `us-central1`, both variables in `deploy/terraform/variables.tf`).
- `deploy/terraform/wif.tf` and `artifact_registry.tf` implement this naming.

This clause and its identity are CI-deploy identity (GitHub Actions to GCP), unrelated to end-user auth, and are unaffected by the 2.0.0 change.

## 7. Privacy

**DEPLOY-24.** `docs/BRIDGE_SPEC.md`'s "no request logging of note content by default; `--log-notes` opts in for debugging" clause holds by default everywhere, but in the deployed configuration `--log-notes` is forced off unconditionally, the deploy entrypoint does not expose a way to turn it on. Rater note content (the substance of what they observed about the models under test) must never reach Cloud Logging or any GCP-managed log sink. This is a hard requirement, not a default that an operator flag can override, because the deployed surface is reachable over the internet (behind the auth check, DEPLOY-27) rather than a machine only the rater can touch.

**DEPLOY-25.** A log-based metric and alert on repeated `401` and `403` responses (auth failures) from the same source is recommended, so a credential-guessing or wrong-domain access pattern is visible to the operator instead of silently absorbed. *(2.0.0: extended from `401` alone to `401` and `403`, since DEPLOY-29 now distinguishes the two, and a burst of `403`s is its own signal, a valid but disallowed account probing the API, distinct from a burst of `401`s.)*

## 8. What is still deliberately absent

**DEPLOY-26.** No database. No multi-user support, the deployed bridge still serves exactly one rater's workflow, just reachable over HTTPS instead of `127.0.0.1`. No server-side session state; each `/evaluate` and `/polish` call is self-contained per `docs/BRIDGE_SPEC.md`. No clip audio is ever sent to any provider in the deployed configuration either, `docs/STT_SPEC.md` §6 ("No provider ever receives a model clip in the default path") is a rule about what the STT layer does with audio, and hosting the bridge on Cloud Run does not touch that layer's behavior at all. It remains fully binding. Unaffected by the 2.0.0 auth and network change.

## Traceability

This spec supersedes, for the hosted-deployment case only, the following clauses: `docs/BRIDGE_SPEC.md` "Bind `127.0.0.1` only" and "No auth" (superseded by DEPLOY-6 and DEPLOY-9 through DEPLOY-15 respectively), and `docs/ARCHITECTURE.md` "No auth, no multi-user" (superseded by DEPLOY-9 through DEPLOY-15; multi-user remains correctly absent per DEPLOY-26). Both source documents mark their superseded clauses deprecated in place with a pointer back here, per the CLAUDE.md deprecation rule. Neither clause is deleted.

**2.0.0 addendum:** the chain above now has an extra hop. `BRIDGE_SPEC.md` and `ARCHITECTURE.md` point at DEPLOY-9 through DEPLOY-15 for auth and at DEPLOY-6 for ingress; those DEPLOY clauses are themselves now deprecated in place (DEPLOY-9, DEPLOY-10, DEPLOY-11, DEPLOY-12, DEPLOY-14, and DEPLOY-6) and each carries its own forward pointer into DEPLOY-27 through DEPLOY-33. A reader following the original chain from `BRIDGE_SPEC.md` or `ARCHITECTURE.md` lands on a deprecated clause, not a dead one, the chain is walkable end to end, but it is now two hops instead of one. T2 owns updating `BRIDGE_SPEC.md`'s and `ARCHITECTURE.md`'s own deprecated blocks to point directly at DEPLOY-27 through DEPLOY-33 where practical, which would shorten the chain back to one hop; this spec's own obligation is only to make sure its end of the chain is not a dead end, and it is not.
